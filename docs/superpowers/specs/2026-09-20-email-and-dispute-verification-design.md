# TVTMS Ticket Email and Public Dispute Verification Design

## Status and authorization boundary

This document defines the approved design for reliable ticket-email notification and recorded-email verification for public disputes. It is design-only: it does not authorize implementation, database migration, secret configuration, real email, real dispute submission, merging, or deployment.

Implementation must use the existing checkout and a dedicated feature branch based on the latest remote `sync-v4`. Existing tracked and untracked files must be preserved. In particular, no existing file under `docs/superpowers/specs/` may be modified or committed without separate permission. A future push or merge to `sync-v4` requires explicit production-deployment approval because that branch deploys automatically.

The existing React UI/UX, ticket issuance, payment calculations and authorization, administrator workflows, landing-page behavior, and configurable dispute deadline (currently 15 days) remain authoritative unless this document explicitly describes a narrow extension.

`djklintskie@gmail.com` is only an approved future test recipient. It is not an SMTP sender and must not appear as a hardcoded application recipient or sender.

## Confirmed current behavior and root causes

The current request path is Officer -> React `IssueTicket` -> PHP `tickets_create` -> Supabase `tvtms_ticket_create` -> PHP SMTP helper -> recipient.

The investigation confirmed these defects:

1. `.github/workflows/deploy-hostinger-v4.yml` creates production `config.local.php` with SMTP explicitly disabled and with empty SMTP settings. Production health consequently reports SMTP as not configured.
2. `tickets_create` correctly performs database ticket creation before attempting email, but it discards the boolean result from `send_basic_email`. The API and React UI therefore cannot distinguish ticket persistence from mail acceptance or failure.
3. The existing email contains only the ticket number and plate. It omits the required violation, penalty, and public ticket-lookup link.
4. The database already snapshots `owner_email_at_issue` and can fall back to the registered vehicle email for a repeat offender. PHP instead decides whether to send using only the email submitted in the current request. A repeat-offender ticket can therefore have a valid canonical email snapshot but receive no notification.
5. There is no persistent notification attempt record, idempotency key, retry claim, or audit-friendly outcome. A naive retry could duplicate a notification.
6. Public lookup currently avoids returning the owner email, which protects privacy, but it cannot display a server-masked notification address.
7. Public dispute filing requires the complete recorded email on every submission. It has no one-time code, challenge expiry, attempt limit, resend cooldown, ticket binding, or replay protection.
8. The final public-dispute RPC does correctly recheck ticket status, the configured dispute deadline (default 15 days), and an existing open dispute. Those checks must be retained and moved into the atomic verified-submission path.

## Design goals and non-goals

The implementation will:

- Preserve ticket creation even when notification delivery is unavailable.
- Report ticket persistence and SMTP acceptance as separate outcomes.
- Use the email snapshot associated with the newly created ticket.
- Prevent ordinary retries from sending a second accepted notification.
- Expose only a masked email to public clients.
- Replace repeated full-email entry with a ticket-bound one-time-code workflow.
- Recheck all financial, eligibility, duplicate-dispute, deadline, and administrator rules on the server.
- Keep all secrets out of source, logs, browser payloads, and build artifacts.
- Test SMTP through controlled fakes only.

It will not claim inbox delivery. SMTP acceptance only means the configured mail server accepted the message. It will not redesign the pages, weaken payment or authorization rules, send bulk notifications, migrate production automatically, or introduce a third-party authentication provider.

## Data model and migration

One new forward-only Supabase migration will define two server-owned tables and the narrow RPCs needed to update them atomically. The migration file will be prepared and tested but not applied to any production project without explicit approval.

### Ticket email notification ledger

`ticket_email_notifications` records the one issuance notification for each ticket. Its core fields are:

- `id bigint generated by default as identity primary key`
- `ticket_id bigint not null references tickets(id) on delete restrict`
- `notification_type text not null default 'ticket_issued'`
- `status text not null`, constrained to `pending`, `sending`, `accepted`, `failed`, `not_applicable`, or `unknown`
- `attempt_count integer not null default 0`
- `claimed_at`, `last_attempt_at`, `accepted_at`, and `updated_at` timestamps
- `last_error_code text` and a length-limited, sanitized `last_error_message text`
- `created_at timestamptz not null default now()`

A unique constraint on `(ticket_id, notification_type)` is the idempotency authority. The ledger does not duplicate the full email address; the immutable ticket snapshot remains the recipient source. It may record the safe masked address or a keyed recipient fingerprint for diagnostics, but never SMTP credentials.

Server-only RPCs will claim an attempt under a row lock, finalize the result, and reject claims after `accepted`. A failed result may be retried by an authorized officer or administrator. A `sending` attempt that loses its process after SMTP acceptance is inherently ambiguous because SMTP and PostgreSQL cannot share one transaction. After a bounded lease it becomes `unknown`, not automatically retryable. This conservative state avoids silent duplicate mail; a future supervised retry would require an explicit warning and is outside the automatic path.

### Public dispute verification challenges

`public_dispute_verifications` stores short-lived, single-ticket challenges:

- `id bigint generated by default as identity primary key`
- `ticket_id bigint not null references tickets(id) on delete cascade`
- `challenge_token_hash text not null unique`
- `code_hash text not null`
- `status text not null`, constrained to `pending`, `verified`, `consumed`, `expired`, or `locked`
- `attempts_remaining integer not null default 5`
- `requested_at`, `last_sent_at`, `expires_at`, `verified_at`, `consumed_at`, and `created_at` timestamps
- `delivery_status text` and a sanitized `delivery_error_code text`
- a keyed requester fingerprint for ticket/IP rate limiting without storing a raw IP address

The browser receives a cryptographically random 256-bit challenge token and a six-digit code is sent to the ticket email. PostgreSQL stores only `SHA-256(challenge token)` and a keyed HMAC of the code scoped to the challenge and ticket. The HMAC key comes from the existing server-only token secret. A bare fast hash of a six-digit value is prohibited because it is trivial to enumerate offline.

Defaults are a 10-minute expiry, five verification attempts, a 60-second resend cooldown, and bounded hourly request limits per ticket and requester fingerprint. These values are server constants covered by tests. Expired or exhausted challenges cannot be revived. A resend invalidates the previous code and retains the same privacy guarantees.

### Database access controls and reversibility

Both tables will have RLS enabled. All table, sequence, and function privileges will be revoked from `public`, `anon`, and `authenticated`; only the backend `service_role` receives the minimum required privileges. New functions will use an empty `search_path`, schema-qualified objects, explicit input validation, and explicit `EXECUTE` grants. No browser will call Supabase directly for these workflows.

The migration will be additive and will not rewrite existing tickets, payments, disputes, owners, or settings. Its review notes will include exact rollback SQL in dependency order: revoke/drop the new RPCs, then drop only the two new tables and their indexes. Rollback is permitted only before relying on stored notification/challenge history and only after backup/review. Existing tables and functions will never be dropped by the rollback.

## Ticket issuance and email notification flow

The officer form retains its current fields, review behavior, and visual design. `owner_email` remains optional so ticket issuance is not blocked when no address exists. Existing vehicle lookup may still prefill it.

After `tvtms_ticket_create` succeeds, PHP will use the canonical returned ticket email snapshot, not the raw request value. The ticket response must provide the saved ticket even if every later notification step fails.

The server flow is:

1. Save the ticket through the existing transaction.
2. Read the canonical ticket number, ticket ID, recorded email snapshot, violation, penalty, and plate from the returned result.
3. If no valid canonical email exists, persist `not_applicable` and return a non-error notification outcome.
4. Otherwise atomically claim the unique notification ledger row.
5. Build an escaped HTML and plain-text-safe message containing ticket number, violation, penalty, plate, and `https://trafficviolation.dcsbisu.com/ticket-lookup?ticket=<encoded ticket number>`.
6. Attempt SMTP once and finalize the claimed ledger row with a structured result.
7. Return HTTP 201 for the successfully created ticket regardless of mail outcome, with a separate `notification` object.

The response contract is:

```json
{
  "success": true,
  "message": "Ticket issued successfully.",
  "ticket": {},
  "notification": {
    "status": "accepted|failed|not_applicable|already_accepted|unknown",
    "recipientMasked": "dj***@gmail.com",
    "retryAllowed": false,
    "message": "Ticket saved. The mail server accepted the notification."
  }
}
```

The UI will render ticket success separately from the notification result and will use precise wording. It must never equate SMTP acceptance with inbox delivery. Navigation to the new ticket may continue, but the status must remain visible long enough to understand, or be shown on the ticket details page.

An authenticated `POST /api/tickets/{id}/notification/retry` route will reuse the same claim/finalize logic. Apprehending officers may retry only notifications for tickets they issued; administrators retain their existing broader authorization. It rejects `accepted`, `sending`, and `unknown` states and never invokes ticket creation.

## Structured mail transport result

The boolean mail helper will be wrapped or replaced with a structured result containing a stable status/error code and no sensitive server transcript. Expected results include `accepted`, `disabled`, `configuration_error`, `invalid_recipient`, `rejected`, and `transport_error`.

For SMTP, `accepted` is recorded only after the server returns a successful response to the completed message data transaction. Connection, TLS, authentication, recipient, or data failures remain failures. Logs may include a stable error code, ticket/notification ID, and sanitized stage, but never passwords, API keys, authentication commands, raw challenge tokens, OTPs, or full recipient addresses.

## Public lookup and masking

The existing public lookup RPC may continue returning an internal ticket ID to PHP. Before the response leaves PHP, the handler will retrieve the canonical ticket email server-side, preferring `owner_email_at_issue` and using the current vehicle email only for a legacy ticket with no snapshot. It will mask that value, add only `notification_email_masked` and `has_notification_email`, then remove internal IDs and verification metadata.

The masking helper will normalize and validate the address, keep at most the first two local-part characters, replace the remainder with `***`, and retain the domain for recognizability. For example, `djklintskie@gmail.com` becomes `dj***@gmail.com`. A one-character local part becomes `d***@domain`. Missing or invalid values produce `has_notification_email: false` and no recoverable address fragment.

The React ticket card adds one detail row:

- `Notification Email: dj***@gmail.com`, or
- `Notification Email: No email recorded`

No public endpoint may return `owner_email`, a full address, owner name, owner address, driver-license data, receipts, database IDs, challenge hashes, or verification state. Existing history, penalties, paid amount, remaining balance, status, search modes, and layout remain unchanged.

## Public dispute verification flow

The current dispute card, typography, ticket selection, notices, and reason field remain in place. Only staged verification controls are added inside the existing layout.

### 1. Select and request

An eligible ticket shows its masked notification address and a `Send verification code` action. `POST /api/public/dispute/verification/request` accepts only the ticket number. PHP rechecks that the ticket exists, is unpaid, is inside the configured deadline, has no open dispute, and has a valid recorded email. The database RPC locks the ticket/challenge scope, enforces cooldown and rate limits, invalidates prior active codes where appropriate, and creates the hashed challenge.

PHP sends the code to the canonical ticket snapshot. The response never includes the code or full address. It returns the opaque challenge token, masked address, expiry duration, resend delay, and an accurate mail-acceptance outcome. A failed send marks the challenge delivery failure and cannot be verified.

### 2. Verify

`POST /api/public/dispute/verification/verify` accepts ticket number, challenge token, and six-digit code. PHP hashes the token, derives the keyed code digest, and calls a locking RPC. The RPC verifies ticket binding, delivery status, expiry, challenge status, and attempts remaining before comparing fixed-length keyed digests. Each wrong code decrements attempts atomically. Success marks the challenge `verified`; exhausted attempts mark it `locked`.

The raw challenge token remains only in React component memory, is never placed in a URL or persistent browser storage, and is cleared when the selected ticket or lookup mode changes.

### 3. Submit

After verification, the existing reason field is enabled. `POST /api/public/dispute` accepts ticket number, challenge token, and a 10-4000 character reason; it no longer accepts or compares a full email.

A replacement server-only RPC locks the ticket and challenge, verifies their binding and verified/unconsumed state, and then rechecks all authoritative rules in the same transaction:

- ticket exists and remains `unpaid`;
- the current `system_settings.dispute_deadline_days` value, default 15, has not elapsed;
- no `submitted` or `under_review` dispute exists;
- the ticket's current lifecycle/payment-derived status remains eligible under the existing rules;
- the challenge is unexpired, verified, and unused.

Only then does it insert the public dispute and administrator notifications and mark the challenge `consumed`. A replay receives a conflict response and cannot create another dispute. Existing administrator review/approval authority and the rule preventing approval after payment remain unchanged.

## Rate limiting and abuse controls

The existing filesystem IP limit remains as an outer low-cost control, with separate buckets for code request, verification, and final submission. Database enforcement supplies the authoritative per-ticket cooldown, attempt count, replay protection, and hourly limits so PHP worker concurrency cannot bypass them.

Responses use `429` and `Retry-After` for cooldown/rate limits, `400` for malformed input, `403` for deadline/status ineligibility, `409` for duplicate/replayed state, and generic messages where extra detail would expose sensitive verification information. All public responses remain `Cache-Control: no-store`.

## SMTP and deployment configuration

The deployment workflow will eventually read these GitHub Actions secrets without printing them:

- `SMTP_HOST`
- `SMTP_PORT`
- `SMTP_SECURE`
- `SMTP_USERNAME`
- `SMTP_PASSWORD`
- `SMTP_FROM_EMAIL`
- `SMTP_FROM_NAME`

The workflow will validate presence and safe values, create the private `deploy/api/config/config.local.php` under `umask 077`, enable SMTP only when the complete validated configuration is present, run PHP syntax/config-readiness checks, and continue excluding the private file from source control and ordinary build artifacts. The API health endpoint may report only `configured` or `not_configured`; it must not expose hostnames, usernames, sender addresses, or secrets.

Until the adviser adds valid provider settings as GitHub Secrets, code can be verified with a fake SMTP server but live email remains explicitly unverified. The future production release is blocked if required SMTP configuration is incomplete.

## Test strategy and acceptance criteria

Implementation follows test-first development. Automated tests must never use production Supabase, production SMTP, the live dispute endpoint, or a real recipient.

Required coverage includes:

1. Ticket issuance with a newly supplied valid email uses the canonical snapshot and returns separate persistence/mail results.
2. Ticket issuance without any stored email succeeds and returns `not_applicable`.
3. Repeat-offender issuance with an omitted request email uses the previously stored canonical ticket snapshot.
4. Fake SMTP acceptance records `accepted`; authentication, connection, recipient, and data failures record accurate failures.
5. A retry does not create a ticket and cannot resend an `accepted`, `sending`, or `unknown` notification.
6. Concurrent retry claims permit only one sender.
7. Notification content contains the correct ticket number, violation, penalty, plate, and encoded public lookup link.
8. Public lookup returns the expected masked address and never the full address or other private owner data.
9. Missing/invalid recorded email produces the safe public message and blocks code requests.
10. Code values and raw challenge tokens are absent from database rows, logs, and response fields other than the browser's opaque challenge token.
11. Valid code verification succeeds once; wrong codes decrement attempts; exhausted, expired, superseded, mismatched-ticket, and replayed challenges fail.
12. Resend cooldown, per-ticket/requester rate limits, and HTTP `Retry-After` are enforced.
13. Final submission requires a verified challenge and atomically consumes it.
14. Paid, cancelled, deadline-expired, or already-disputed tickets remain ineligible; the configured 15-day default remains unchanged.
15. Payment totals, mark-unpaid behavior, ticket search/history, officer ownership restrictions, administrator authorization, public landing/redirect behavior, and existing role tests remain green.
16. The deployment workflow fails safely when SMTP secrets are incomplete and never prints their values.

Verification commands will include existing contract tests, JSX verification, PHP syntax checks for every PHP file, the full automated suite, and `npm run build:hostinger`. SQL migration tests will use an isolated/disposable database when available. If no PostgreSQL/Supabase runtime is available, structural tests and PHP mock tests will run and the missing runtime verification will be reported rather than inferred.
