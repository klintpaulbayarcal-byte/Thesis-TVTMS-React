## 1. Implemented and investigated

1. **Ticket/penalty preview and history:** independent request-generation gates ignore delayed responses after switching plates/violations; old history cannot overwrite a newly selected plate. Displayed amount is a preview, actual fine comes from backend issuance. Read-only production snapshot on September 21 showed zero active escalating-fine rules, one Counterflow ticket and zero Defective Lights tickets; the video's cross-violation Level 2 is not evidence of an increased issued fine. No fine schedule, SQL calculation, or historical ticket rewritten.
2. **Ticket email creation, retry, SQL fallback (Task 3):** `tickets_create` persists a ticket even if recipient confirmation is declined, and sends email only if the officer affirmatively confirms the current address. Retry requires a freshly entered address plus explicit confirmation. PHP independently validates `tickets.owner_email_at_issue` by exact ticket ID before the SQL claim, requires an identical normalized recipient and matching ticket ID in the returned SQL claim before SMTP, and fails closed for missing/mismatched/stale values. A mismatched claimed attempt is finalized as failed; if finalization cannot be confirmed, automatic retry remains disabled. Isolated tests exercise missing confirmation, changed address, stale vehicle fallback, claim ticket mismatch, sender failure/uncertain finalization and save-without-email. SQL `tvtms_ticket_email_claim` **still contains its original fallback to mutable vehicle email**, but the protected PHP sender cannot use that fallback under these checks. A database-enforced removal of the legacy SQL fallback would require a separately approved migration. Existing SQL role checks still restrict officers to their own tickets; no SQL migration applied. SMTP `accepted` is NOT proof of inbox delivery.
3. **Location/reporting:** old coordinate-only entries displayed explicitly as `Coordinates: ...`, not invented places or inferred geographic risk; report counts remain unchanged, no geocoding or schema change.
4. **Dashboard loading and payment:** Officer/Admin/Analytics distinguish loading, genuine zero/empty results, and partial endpoint failures; partial payments show `Partially Paid` using the backend-derived payment status while preserving stored ticket lifecycle and payment records.
5. **UI Task 7:** isolated Chromium at 1440px and 375px verified cramped notification timestamp and `View Message` had no vertical separation; a scoped stylesheet now supplies an 8px gap with no horizontal overflow in those isolated checks. An additional reproduced landing `#search-card` navigation target sat under the sticky header; applied matching existing scroll-margin (96px desktop, 86px mobile). Existing FAQ and Contact anchor offsets passed isolated CSS checks, so left unchanged. Hero background was visually busy in the recording but its title remained readable; no subjective redesign or speculative overlay change. These browser checks use representative markup and current CSS, **not** an authenticated running React browser session.
6. **Review decision:** the email confirmation UI uses native browser confirm/prompt at the final API send boundary instead of the plan's custom modal checkbox. This minimizes modifications to the existing ticket/detail screens and ensures confirmation against the current email immediately before a request. Cost: less refined UX and automated-browser dialog handling; future custom modal can be a separately reviewed UI enhancement. Replaced outdated sender assumptions in the email test fixtures; the new explicit-confirmation tests verified the before/after behavior. Self-review by the implementing assistant only, no independent fresh reviewer was available; a second-person code review before production is advisable.

## 5. Release gate, restrictions and rollback

**Do not deploy automatically.** Before a production release: (a) review and decide on two outstanding production dependency advisories and plan compatible major-version upgrades or explicitly document/accept residual risk after security assessment; (b) arrange an independent code review, ideally with authenticated nonproduction end-to-end tests using safe fixture accounts; (c) snapshot production database and existing Hostinger files with secure backup/restore procedure; (d) verify correct GitHub secrets without displaying them, exact hosting destination, release SHA, workflow deploy conditions and migrations already applied; (e) obtain explicit user approval for deploying this exact reviewed feature commit. The current SQL email claim fallback remains and must only be accessed through the strict sender path until an approved migration removes it.

The release branch `sync-v4` automatically deploys on push. After **separate** approval, compare `sync-v4` against feature HEAD again, perform a reviewed fast-forward/cherry-pick strategy (never merge PR #1 automatically), let guarded CI/build/FTPS run, verify `/api/health`, public portal and authenticated functional smoke checks and mail recipient only with user approval. If release fails, use a reviewed revert commit and guarded deploy plus verified Hostinger/database backups—not force-push or unapproved SQL deletion. Production QA markers remain untouched until separately approved backed-up cleanup.

**As of this report:** implementation fixes and automated checks PASS; full production E2E and independent review NOT VERIFIED; npm security audit still reports advisory findings. Production branch, live Hostinger, credentials, database, historical records, QA records, PR #1, and real mail remain untouched by this work. Await user deployment approval, but never conflate deployment approval with permission to make a major dependency upgrade or SQL migration.
