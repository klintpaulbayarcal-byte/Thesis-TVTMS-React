# Reversible API write-free release window

This procedure is prepared and tested locally on Apache. It has not been installed or enabled on Hostinger. Installing the gate or its marker files on production is the first production write and requires the single release authorization after all backup and QA gates pass.

`api/.htaccess` now includes a small gate. When `<DOCUMENT_ROOT>/api/.release-write-lock` exists, normal POST/PUT/PATCH/DELETE requests receive HTTP 503. GET/HEAD/OPTIONS remain readable. A temporary `tvtms_release` cookie must contain a random 64-character lowercase hex token and match an existing `.release-operator-<token>` file to bypass maintenance. Normal application login, role checks and authorization still apply. Marker-file HTTP reads are denied. No marker is committed or enabled. The packager excludes markers before copying; the guarded NO DELETE FTPS upload preserves existing live markers throughout the version gap.

Before the release window, verify the actual TVTMS Hostinger document root and that Apache honors these rules. Record the private operator/browser access method. The local test runs the real `.htaccess` with disposable Apache runtime files and verifies ordinary writes are blocked, invalid/unknown tokens fail, only the matching cookie passes, marker files cannot be fetched, and removing the lock restores previous behavior. Live hosting behavior must be verified immediately after authorized activation; if this fails, do not migrate.

After authorization:

1. Record the release start time and refreshed aggregate counts. Confirm the verified database and live-file backups cover current state. Preserve the existing live `api/.htaccess` privately.
2. Install the reviewed gate rules in the live `api/.htaccess`, retaining existing policies. Privately generate a cryptographically random 32-byte token; create empty `api/.release-operator-<64-hex-token>` and `api/.release-write-lock` files. Never place the token in a URL, Git, report, or log. Keep the operator marker path private.
3. In the approved release operator's browser, set the temporary cookie for `https://trafficviolation.dcsbisu.com`: name `tvtms_release`, value the private token, path `/api`, Secure, HttpOnly, SameSite=Strict, short expiry covering the window. Use the browser's local cookie editor; no new application account or persistent credential is needed.
4. From a normal browser/client without this cookie, verify representative citation, payment, public dispute, and Admin write routes return 503. Use unsigned/invalid fixture bodies so failure of the gate cannot create records. Verify an operator request still encounters normal auth/validation. Preserve evidence without cookie/header values. Keep writes blocked if any normal path escapes.
5. Apply only the September 30 migration after its approval and directly verify schema, historical data and RPCs. Perform tracking-only repairs if needed; never rerun September 22/27 SQL. Merge/push/deploy through the guarded workflow while the lock remains present. The marker is independent of PHP configuration and does not get removed by the workflow.
6. Use the authenticated Administrator UI with the operator cookie to set the exact supplied Officer rank. Perform the single approved citation smoke test and other approved checks. If no real email recipient was authorized, temporarily disable SMTP through reviewed private production configuration before creating that test citation, verify the ledger result, then restore the original SMTP setting. Do not use an unapproved real recipient.
7. Resume only after every required DB/deployment/rank/privacy/accounting/smoke check passes. Remove the write-lock marker, remove the operator marker, clear the temporary cookie, and record the exact resume time. Removing the lock restores normal behavior; no DB/schema change is needed to disable maintenance.

If migration or deployment fails, keep the lock. A successful revised migration can make the old PHP RPC contract incompatible, so an old-frontend-only rollback is insufficient. Prefer a reviewed forward fix or a coordinated DB/application restore from verified backups, accounting for any newer records. The known source rollback SHA is `f1c05fdb8dd1f42ab6b585c7311f44105cc2fcc9`.

Reserve a 30–45 minute low-use window. Operator cookie setup and gate activation should precede schema changes; DB verification, deployment, rank configuration and smoke checks occupy the rest. No window has been scheduled or activated in this preparation.
